# Durable room worlds and optional Pear nodes

The live WebRTC browser host or dedicated WebSocket server remains the single room authority. `RoomPersistence` takes a bounded snapshot every five seconds, signs it with a locally owned ECDSA P-256 key, saves the private owner backup, then broadcasts the public envelope. Visitors verify and retain that envelope. There is no client message that imports or replaces authority state, no automatic host election, and no claim that signatures prove an honest economy.

Each browser connection asks the authority to sign a fresh 256-bit nonce and room code. WebRTC proofs additionally bind the host's actual DTLS SHA-256 certificate fingerprint, read from the negotiated connection on both sides. Known-world clients verify the pinned key before sending their private reconnect credential, then require a valid pinned checkpoint before applying welcome, world, combat or machine state. A replayed old checkpoint alone cannot answer that nonce. Fresh unknown hosts use trust on first use; possession of their key does not prove fair gameplay. WebSocket proofs use the nonce but do not carry an RTC fingerprint; remote WebSocket transport still requires WSS for channel protection.

`room-checkpoint.ts` exports `signRoomCheckpoint`, `verifyRoomCheckpoint` and `roomCheckpointTopic`. The envelope has a monotonic revision, previous-envelope hash, timestamp, public key and generated-world state. Its signature covers canonical JSON; its identifier hashes that payload and signature. The topic is SHA-256 of `verso-world-v1|room|seed|generation|publicKey.x|publicKey.y`. Visitors pin the first observed authority, reject different keys and older revisions, and check the parent link for adjacent revisions. They may miss intermediate snapshots; this is verified latest-state replication, not consensus or proof that every intermediate action was legal.

Only the private owner backup contains the signing key, authenticated member reconnect tokens, action replay records, unacknowledged combat receipts and proximity-chat history. The public state contains World chat, generated enemy consequences, shared resources/doors and production receipts. Do not publish the private storage directory. Personal inventories, story and health remain separate game saves, so this is not a transactionally unified MMO database.

Browser storage keeps at most 24 owned/replicated worlds and 64 room credentials. Ownership cannot be recovered from a public replica after deleting the private key. `hostSavedWorld(code, identity)` verifies a locally owned checkpoint and restores that same room; a visitor cannot call it with a replica. Hosts must stay online for live play. Server disk files are atomically replaced, restored before listening, and flushed on orderly close. Abrupt termination can lose the latest five-second interval; unavailable/full storage is reported rather than silently called durable.

`hostPublicWorld(code, identity)` can create a new authority at a deterministic discoverable code, or resume an owned world. It refuses to replace a locally pinned visitor replica with a new writer. A collision with an already live host is an explicit connection failure so the UI can discover and join the winner. A public room code is a rendezvous address, not permission to seize a previous owner's signed planet.

## Pear compatibility

Pear is an installed runtime rather than an API that a GitHub Pages page can directly enable. Its official desktop architecture places Hyperswarm, Hypercore and persistent storage in a native Bare worker behind IPC; the web renderer stays a normal web view. Keeping our existing browser WebRTC transport and adding an optional native storage node follows that separation. [Pear desktop architecture](https://docs.pears.com/explanation/pear-desktop-architecture/).

Hypercore supplies append-only replicated logs, verified reads and sparse replication; Corestore manages multiple such logs. These support an optional node retaining signed public world checkpoints while gameplay continues through the room authority. They do not validate our combat rules or convert locally declared inventories into an authoritative economy. [Hypercore reference](https://docs.pears.com/reference/building-blocks/hypercore/), [Pear storage and replication guides](https://docs.pears.com/how-to/store-and-replicate/).

The implemented optional [`pear-node/` package](../../pear-node/README.md) is separate from the browser bundle and root dependency tree. It receives `POST /api/checkpoints` from an operator-configured publisher, verifies the game signature and topic history, and appends public envelopes to native replicated storage. Availability requires someone actually running and retaining that node; no hosted Pear service is implied.

The dedicated game server can publish with `VERSO_PEAR_BRIDGE_URL` and `VERSO_PEAR_BRIDGE_TOKEN` (an operator secret of at least 32 characters). `server/pear-checkpoint.mjs` sends only the public envelope, with a three-second request deadline. A failed replica upload reports an optional-bridge outage without rolling back an already saved local world or its revision. Keep bridge credentials out of the frontend. Node installation, limits and replication verification belong to the package's own README and tests.

## Native replication proof

At `fde8d7b`, the isolated package passed four integration tests in 2.027 seconds using real Corestore/Hypercore, two native Hyperswarm instances and a local HyperDHT test network. Signed updates crossed an encrypted peer connection; both nodes restarted from their own disk directories, retained the original writer key and revision pin, and continued replication. A mirror stayed read-only. Invalid public signatures, private fields, conflicting revisions and transport-valid malicious blocks did not replace the exposed checkpoint. Tests also exercised HTTP authorization/origins, upload size and concurrent feed limits.

The service is a native **Node** bridge using Pear ecosystem libraries. No browser WebAssembly runtime or packaged Pear desktop distribution is supplied. Tests did not exercise Internet NAT reachability, unattended uptime or public operator deployment. The public log is not encrypted private membership history; local Say chat, signing secrets and reconnect credentials remain excluded. Native installation and exact endpoint/environment instructions are in the package README.
