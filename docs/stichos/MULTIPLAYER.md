# Cooperative rooms

Verso supports up to eight people exploring the same generated terrain, seeing one another's humanoid bodies and gestures, fighting the same hostile raiders and vault guards, and sharing harvest, container and door changes. Live rooms use a single authority, with signed world checkpoints for durable restoration. Story decisions, body possessions and personal survival remain individual.

## Browser rooms on GitHub Pages

Open **Room**, use **Browser room**, and leave the room code blank to host. Share the displayed code, full invitation link or QR. A full invitation selects the planet and geography; code-only discovery can obtain those details from an available browser host before resident creation. Up to eight people share the room. PeerJS supplies connection discovery through its public signalling service; game messages travel over WebRTC data channels to the hosting browser. No separate game-server account is required for this mode. **Galaxy → Open public frequency** uses a deterministic rendezvous code for a planet; it joins an available authority or attempts to host that code. This is not evidence of a continuously online global planet service.

The host must keep the game open. Leaving, reloading or closing the host interrupts the live room; its original browser can host the saved world again under the same code. There is no automatic host migration. Visitors see an interrupted connection and cannot continue shared attacks or resource claims independently. A visitor can reconnect while the host remains available. WebRTC discovery and connectivity depend on external signalling and STUN/TURN services; restrictive networks can still fail to connect. The dedicated-server option remains available. The authority stores a private browser checkpoint every five seconds and replicates a signed public copy to visitors. Personal game saves stay on each player's own browser. The same portable room authority validates both transports.

The real-input browser harness `scripts/browser-peer-rooms.mjs` passed six baseline checks against actual public PeerJS signalling on `app-BjgRhE0e.js`: two independent browser contexts, visible movement and gestures, exactly one final-stroke harvest winner, retained depletion on visitor rejoin, explicit host-departure disconnection and no browser exceptions. This baseline predates shared PvE. Evidence records the tested build in `.dream-loop/stichos-peer-rooms/results.json`; it does not by itself verify the subsequent combat integration.

## Run on a local network

Use Node 26 and install dependencies with `npm install`. Start the game with `npm run dev` (configured port 4173), or build and preview it with `npm run build` and `npm run preview -- --port 4174`. In a second terminal run `npm run server`. The room service listens on `0.0.0.0:4175`; its WebSocket address is `ws://<host>:4175/ws`. Open the frontend through the same hostname or LAN address used in that WebSocket address. A second player needs the host's LAN address, not their own `localhost`.

The creating player receives a room code. Connections still require matching seed and generation; invitation and discovery UI select them before joining. Existing generation 1 and 2 worlds retain their terrain; generation 3 is supported. The room does not import a creator's previously removed resources or opened containers: shared claims begin when the room is created, while each body retains its local inventory and prior save history.

`HOST` and `PORT` override the room server's bind address and port. By default browser connections are accepted only when the frontend and server use the same localhost or private LAN hostname/IP. For an explicitly configured origin, set `VERSO_PUBLIC_ORIGIN=https://game.example` or comma-separated `VERSO_ALLOWED_ORIGINS`. Public hosting needs a reverse proxy providing HTTPS/WSS; do not expose this development service as a complete account or MMO backend.

## What is shared

- Presence: name, generated appearance, position, heading and walking phase. Positions are client reported and checked against finite clear terrain; the server does not simulate movement or enforce travel speed.
- Resource claims: the server reconstructs the seeded world, checks the actual nearby object, action kind, target coordinates and timber/ore tool, then accepts exactly one claimant. The successful client performs its local inventory operation after the acknowledgement. Other clients apply the world change.
- Shared PvE: the room host simulates generated raiders and vault guards once. Every participant receives their positions, health, attack warnings, projectiles, deaths and agreed truces. The closest active traveler within detection range draws attention; windups retain their aimed direction, allowing dodges. Cover and shared doors block rays and projectiles. Attacks use the equipped construction's generated properties, bounded character level, combat practice and physical upgrade rank. The host accepts an attack intent, never a requested damage amount.
- Doors: explicit open/closed state and collision are shared. Closed doors block movement and combat; opening makes the doorway passable on every client. A floor-click route approaches a closed door, waits for the shared opening acknowledgement, then continues. Closing over another connected traveler is rejected. Create a new room from clear ground; an existing room permits joining in a doorway it has already opened.
- Chat and gestures: wave, thanks and help, plus plain-text **Local** within 12 tiles and **Room** chat across the current room (protocol channels `say` and `world`). Authority-owned names and timestamps prevent message-field impersonation; the UI must render text literally. Messages are capped at 280 Unicode characters, one per second, and 200 retained entries. Late joins receive only nearby Say history and room-wide World history.
- Production: each authenticated member can register up to eight clear platforms. A sawmill consumes an actual pine and an ore sorter an actual rock within 16 tiles; shared sources have a single persistent winning owner/job receipt. A lost acknowledgement can retry that same job without duplicating output. Materials, prepaid work time and resulting inventory remain local declarations. Garden batches do not claim wild sources.

There is no PvP. Friendly residents are protected from attacks in a shared room; their ordinary lives, conversations and personal quest state are not a shared campaign simulation. Body health, energy, supplies, coins, homes, equipment ownership and survival are still stored by each client. A participant's campaign can recognize a confirmed guard defeat or truce without advancing everyone else's dialogue choices. Household resource orders operate in solo play.

Pause, open dialogue, mind transfer and a fallen body withdraw that traveler from enemy targeting. Missing pose updates also make a traveler inactive after 2.5 seconds. Other active players and their enemies continue; pausing does not pause the room. Disconnecting stops shared attacks and claims until reconnection or an explicit departure from the room.

Each hit and death has a monotonically numbered receipt. The client acknowledges processed receipts; the authority keeps relevant unacknowledged hits and contributor rewards for reconnect. Replayed messages cannot award the same progress twice. A fresh late join receives current wounds, deaths and truces, without earlier rewards. Launched projectiles carry their original body and construction identities: mind transfer does not redirect an old body's on-hit restoration into a new host. A pulse restores its artifact benefit once per strike even when it hits several enemies. Eligible contributors receive combat progress; the killing body's coin reward remains physical.

Clients check capacity before resource claims and freeze the pending local interaction until acknowledgement. A disconnect during a claim can leave its outcome uncertain; reconnect refreshes the shared world and never awards a second harvest automatically. Rooms begin with generated combat state and new shared claims, while local save history remains available; they do not import an entire creator's campaign or inventory.

## Lifetime and limits

The origin stores one stable browser player ID and private per-endpoint/room reconnect credentials, including the monotonically increasing request serial. A new client instance can authenticate the same retained member after reload. These credentials are not included in presence, chat, public checkpoints or personal life records. Leaving removes the visible peer immediately. Durable authorities retain up to 32 member records per room; capacity can evict an old disconnected record, so browser identity is not a permanent account entitlement.

`npm run server` saves private authority files in `.verso-server/worlds` by default; `VERSO_WORLD_STORAGE` selects another directory. The server restores verified checkpoints before listening and flushes on orderly shutdown. Files and directory are private (0600/0700) and must not be served over HTTP. The browser retains up to 24 worlds, fails visibly if storage is full, and never evicts an owned planet silently. Normal checkpoints are five seconds apart; abrupt process termination can lose the latest interval. A replica does not contain the authority private key or member credentials and cannot take over or replace the original world. The replica verifies the authority signature and rejects rollback, a changed pinned key, and an inconsistent adjacent parent hash. Missing intermediate revisions are not a proof of complete history. Clearing site data removes browser ownership unless separately backed up; a replica alone cannot restore ownership.

Restored shared state includes resource depletion, doors, machines, production receipts, active and streamed wounded enemies, deaths/truces, projectiles, cooldowns and private unacknowledged combat receipts. Spatial speech stays in the private host backup; only World chat enters public signed replicas. Inventories and campaign state remain in personal saves. Creating a fresh room still does not upload a local campaign or its removed-resource set. Tests can opt out of durability, retaining the old 90-second reconnect/30-minute idle expiry; that is not the normal server launch configuration.

The dedicated service bounds room count (64), players per room (8), reconnect records, request receipts, connections, client messages (8 KiB) and update rate. Combat advances at 20 Hz with bounded substeps. A room normally holds at most 256 active enemies, 128 projectiles and 2,048 persistent combat consequences; wounded, dead and pacified actors are not silently reset by cache eviction. Reaching the consequence limit prevents additional damaging consequences rather than resurrecting earlier enemies. Unacknowledged receipts also limit further combat until the client catches up. Client validation bounds incoming enemy and projectile arrays and rejects non-finite positions, malformed appearances and invalid event data before rendering.

The authority checks shared geometry, cooldowns and generated properties. Movement, loadout ownership and bounded progression are still participant declarations, and a browser host controls its room. These checks prevent ordinary races and malformed input; they are not an anticheat guarantee or an authority over local saves. No purchase or premium cosmetic changes combat strength.

`GET /health` reports service readiness, room/player counts and durable-storage health. An optional operator-configured Pear/Hypercore replica bridge receives signed public checkpoints; it has no authority over inventory or gameplay. See [WORLD-PERSISTENCE.md](WORLD-PERSISTENCE.md). The shared HTTP server passes `/api/store/*` requests to the separately configured store handler before reading their bodies, preserving raw webhook signatures. The store is disabled by default; configuring a payment provider is a separate deployment task.
